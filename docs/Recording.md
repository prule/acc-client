# Recording & Replay

Reference for capturing live ACC sessions to disk and replaying them with the simulator.

Two recorder listeners are provided. Pick one:

| Listener | Scope | Output | Use case |
|---|---|---|---|
| [`RecordingSessionListener`](../acc-client-core/src/main/kotlin/com/github/prule/acc/client/RecordingSessionListener.kt) | One CSV per **session** (practice, qualifying, race, etc.) | Preamble + session messages | Default. Replay each session in isolation. |
| [`CsvWriterListener`](../acc-client-core/src/main/kotlin/com/github/prule/acc/client/CsvWriterListener.kt) | One CSV for the whole **connection** | Every inbound message from connect to disconnect | Long-form capture, debugging across sessions. |

The simulator (see [Replay](#replay)) accepts either format — both write the same row schema.

## CSV schema

Every row: `date,type,hex,json`

| Column | Type | Meaning |
|---|---|---|
| `date` | ISO-8601 local date-time | Wall-clock receipt time. Not used by replay. |
| `type` | int (1–7) | First byte of the UDP payload — message type discriminator. See [type table](#message-type-byte). |
| `hex` | hex string | Full UDP payload, lowercase, no separators. Replay parses this directly. |
| `json` | JSON string | Decoded message — for inspection only; replay ignores it. |

The `hex` column is the source of truth for replay. The `json` column is convenience output from `JsonFormatter` and may be empty if re-parsing failed.

### Message type byte

| Byte | Type |
|---|---|
| 1 | `REGISTRATION_RESULT` |
| 2 | `REALTIME_UPDATE` |
| 3 | `REALTIME_CAR_UPDATE` |
| 4 | `ENTRY_LIST` |
| 5 | `TRACK_DATA` |
| 6 | `ENTRY_LIST_CAR` |
| 7 | `BROADCASTING_EVENT` |

## RecordingSessionListener

One CSV per session. Each file starts with the preamble (track data + entry list + per-car entries) so it is self-contained and replayable without external context.

### Wiring

```kotlin
val context = ClientContext()
AccClient(AccClientConfiguration("MyClient", port = 9000, serverIp = "127.0.0.1"))
  .connect(
    listOf(
      LoggingListener(),
      ContextUpdater(context),
      SessionDetector(
        context,
        listOf(RecordingSessionListener(Path.of("./recordings"))),
      ),
    )
  )
```

`ContextUpdater` MUST precede `SessionDetector` — see [SessionContextStrategy.md](SessionContextStrategy.md).

### Output

- Directory: the `Path` passed to the constructor. Created if missing.
- Filename: `simulator-recording-<localDateTime>.csv`, with `:` replaced by `-` for filesystem safety. Example: `simulator-recording-2026-05-04T18-49-26.591594.csv`.
- One file per session — opened on `onSessionStart`, closed on `onSessionStop` (including connection drop).

If `directory` is `null`, recording is disabled (the listener is a no-op).

### Preamble

On `onSessionStart`, the listener writes (in order):

1. Most recent `TRACK_DATA` bytes.
2. Most recent `ENTRY_LIST` bytes.
3. Each `ENTRY_LIST_CAR`, sorted by `carId` for deterministic replay.

These come from [`ClientContext.snapshotRawPreamble()`](../acc-client-core/src/main/kotlin/com/github/prule/acc/client/ClientContext.kt) — byte-perfect copies, not re-encoded. The `json` column is regenerated by re-parsing the bytes.

After the preamble, every `onSessionMessage` call appends a row.

### Caveats

- Sessions detected via `REALTIME_UPDATE.phase`. If a session ends without a `POST_SESSION` / `SESSION_OVER` phase (rare — usually because the client disconnected first), the file is still closed via `onSessionStop` from the connection-loss path.
- If the connection drops mid-session and reconnects, a new file is opened on the next phase transition into an active state.
- The listener does not buffer — rows are written synchronously per message. CSV writer flushes on close.

## CsvWriterListener

Records the whole connection to one file. Opened on `onStart`, closed on `onStop`. Same row schema. No preamble logic — every message is appended in arrival order.

```kotlin
AccClient(config)
  .connect(
    listOf(
      LoggingListener(),
      CsvWriterListener<AccBroadcastingInbound>(Path.of("./recordings")),
      ContextUpdater(context),
      SessionDetector(context, listOf(...)),
    )
  )
```

Use this when you want a single replayable stream covering multiple sessions, or for debugging the full connection.

## Replay

The [`AccSimulator`](../acc-client-core/src/main/kotlin/com/github/prule/acc/client/simulator/AccSimulator.kt) replays a CSV by:

1. Listening for the client's register packet.
2. On register, sending each row's `hex` bytes to the client at a fixed interval.

Replay is **not** real-time — there's a fixed `millisDelay` between messages (default 100 ms). Original timestamps in the `date` column are ignored.

### Running

```kotlin
val simulator =
  AccSimulator(
    AccSimulatorConfiguration(
      port = 9000,
      connectionPassword = "asd",
      playbackEventsFile = FileSource("./recordings/full-race-donington.csv"),
    )
  )
simulator.start().join() // start() is non-blocking; join() blocks the caller until the receive loop exits
// or call simulator.stop() from another thread
```

Or via Gradle:
- `./gradlew :acc-client-core:runAccSimulator` — boot the simulator directly with the config in `main`.
- `./gradlew :simulator-grpc-server:runSimulatorGrpcServer` — boot a gRPC server that lets external apps `Start` / `Stop` / `Status` the simulator. See [SimulatorGrpcControl.md](SimulatorGrpcControl.md).

### Source variants

| Source | When to use |
|---|---|
| `ClasspathSource("com/github/prule/acc/client/simulator/playback-events.csv")` | Bundled fixtures — read from JAR resources. |
| `FileSource("./recordings/foo.csv")` | Files on disk. Path is relative to the JVM working directory. |

### Adjusting playback speed

Pass `delay` to `AccSimulatorConfiguration` (milliseconds between messages). Faster delay = denser playback; the client's `updateMillis` registration setting still controls how often a real ACC server would push updates, but the simulator ignores that.

## Recording → replay loop

A typical dev flow:

1. Connect to a real ACC server with `RecordingSessionListener` configured.
2. Drive a session in ACC.
3. Stop the client. CSV files appear in the recordings directory.
4. Point `AccSimulator` at one of those files via `FileSource`.
5. Run the simulator + your client (with whatever listeners you're developing). The simulator replays the captured session — no game required.

Bundled example: `acc-client-core/src/main/resources/com/github/prule/acc/client/simulator/playback-events.csv` contains one of each message type (1–7) for smoke testing.
